# Range-finder height reference over indoor obstacles (Gazebo SITL)

Validation harness for the EKF2 behaviour when the downward range finder is
the height reference (`EKF2_HGT_REF=2`, `EKF2_RNG_CTRL=2`) and the vehicle
flies over furniture. It compares the two settings of `EKF2_RNG_OBST`:

* `0` – current behaviour: the EKF height follows the range finder, so the
  vehicle terrain-follows (climbs over a table, descends behind it, and can
  keep a height offset afterwards);
* `1` – hold altitude over obstacles: a change of the measured distance that
  the inertial height propagation does not explain is attributed to the
  surface below as soon as two consecutive range samples agree on it, and the
  height is kept.

The vehicle is an x500 with optical flow and a ToF-like downward range finder
(12 m, 2 cm noise), no GPS unless requested. Ground truth from Gazebo
(`vehicle_local_position_groundtruth`) is logged next to the estimate so the
physical altitude can be compared with the estimated one.

## Requirements

* `build/px4_sitl_default` built (`make px4_sitl` is enough; the script uses
  `build/px4_sitl_default/bin/px4` and `rootfs/gz_env.sh`),
* Gazebo Harmonic (`gz sim` 8.x) with a GPU that can render sensors headless
  (OGRE2/EGL). If sensors do not render, try `--render-engine ogre`,
* Python 3 with `mavsdk` (3.x, gRPC), `pyulog`, `numpy`, `matplotlib`, `Pillow`.

## Running

From the repository root (any working directory works, paths are absolute):

```sh
# no GPS, terrain following (baseline)
python3 test/sitl_rng_obstacle/fly_furniture.py --obst 0 --out /tmp/rng_obst0

# no GPS, hold altitude over obstacles
python3 test/sitl_rng_obstacle/fly_furniture.py --obst 1 --out /tmp/rng_obst1

# with (simulated) GPS fused as well
python3 test/sitl_rng_obstacle/fly_furniture.py --obst 1 --gps --out /tmp/rng_obst1_gps

# then, for each run
python3 test/sitl_rng_obstacle/analyze.py /tmp/rng_obst0/*.ulg --out /tmp/rng_obst0
```

Options: `--speed` (cruise speed of the fast passes, default 3.0 m/s),
`--alt` (default 1.5 m), `--alt-trim`, `--doors`, `--out` (default
`runs/<timestamp>_obst<N>[_gps]` next to the script), `--render-engine`,
`--keep` (leave gz and PX4 running), `--video` (see below).
A run takes about 3 minutes; every step has a timeout.

Each output directory receives the flight log (`<time>.ulg`), `px4.log`,
`gz.log` and `run_info.json` (parameters, status, wall time, whether the
doorway legs were flown). `analyze.py` adds `altitude.png` and
`metrics.json`.

The script kills stale `px4`, `gz sim` and `mavsdk_server` processes before
it starts, launches the Gazebo server headless, spawns the model itself
(`x500_flow_tof_0` at the spawn point) and starts PX4 with
`PX4_GZ_MODEL_NAME` so that PX4 attaches to the existing model. All PX4
parameters are passed as `PX4_PARAM_*` environment variables; a parameter the
binary does not know (e.g. `EKF2_RNG_OBST` on an older build) only produces a
`param set` error in the startup output and the run continues.

## Video

```sh
# film while flying (two extra cameras; slows the simulation, see below)
python3 test/sitl_rng_obstacle/fly_furniture.py --obst 1 --video --out /tmp/rng_obst1

# or film a flight that was already logged, without touching the flight
python3 test/sitl_rng_obstacle/replay_video.py /tmp/rng_obst1/*.ulg --out /tmp/rng_obst1_video
```

Both produce `wide.mp4` (corner of the living room), `side.mp4` (camera at
1.05 m on the south wall, level, so the altitude can be judged against the
furniture) and `flight.mp4` (side view with the corner view as an inset,
needs `ffmpeg`). The cameras are the `flight_cameras` model (960 x 540,
15 fps, `CameraVideoRecorder` plugin with simulation-time stamps).

`--video` renders and encodes the two cameras during the flight, which
brings Gazebo down to roughly a third of real time on this machine. The
route timing does not suffer (the speed profile runs on the PX4 clock, read
from the odometry / IMU timestamps in the telemetry), but the simulated
optical flow gets noticeably worse when the simulation runs that slowly
(flow innovations about three times larger), so filmed flights without GPS
drift more and abort more often. `replay_video.py` avoids that: it runs
the world without PX4, spawns the vehicle model as a static model and sets
its pose from `vehicle_local_position_groundtruth` /
`vehicle_attitude_groundtruth` at the current simulation time (from the
world statistics topic; needs the `python3-gz-transport13` /
`python3-gz-msgs10` bindings). Propellers do not spin in a replay.

## Flight route

Offboard mode, position + velocity-feedforward setpoints at 20 Hz along a
trapezoidal speed profile, `--alt` above the floor, yaw held. The vehicle
settles at every waypoint (within 0.3 m and below 0.4 m/s) before the next
leg starts.

1. spawn point in the living room, climb to `--alt`; flow quality, EKF
   fusion flags and `dist_bottom` are read through the PX4 shell and printed
   (the EKF height creeps up ~0.15 m between arming and take-off, so the
   range finder reads ~0.15 m less than `--alt` at the setpoint; `--alt-trim`
   adds a fixed offset if a specific true altitude is wanted);
2. slowly (1 m/s) over the 0.15 m step platform and off it again;
3. fast (`--speed`) pass over the dining table, slow (1 m/s) pass over the
   coffee table, fast pass over the couch, 4 s hover directly above the
   dining table, slow leg off the table, return to the spawn point;
4. `Action.land()`, wait for disarm, shut down PX4 and gz, copy the newest
   `.ulg`.

With `--doors` the vehicle additionally flies (before step 3) slowly through
the hallway doors into the bedroom, fast over the bed and back. This is off by
default: without GPS the flow/range position estimate was repeatedly lost in
the doorways (see below).

## What the plots show

`altitude.png` has three panels sharing the time axis:

1. **Altitude** – true altitude (ground truth), estimated altitude (EKF `-z`)
   and the setpoint altitude, all as height gained above the resting position
   on the floor. With `EKF2_RNG_OBST=0` the estimate drops when the range
   finder sees a table and the vehicle physically climbs (terrain following);
   with `EKF2_RNG_OBST=1` the true altitude should stay flat. The grey band
   is the cruise segment used for the metrics.
2. **Range** – raw range-finder measurement and the EKF `dist_bottom`
   (height above ground / obstacle). Samples where `dist_bottom` is invalid
   are marked.
3. **Range height fusion** – `estimator_aid_src_rng_hgt` innovation with
   rejected samples marked in red, plus the `dist_bottom` and `z` reset
   counters (right axis).

`metrics.json` (cruise segment: from the estimate settling at the commanded
altitude to the landing command):

| key | meaning |
| --- | --- |
| `true_alt_max_dev_m`, `true_alt_rms_dev_m` | max / RMS deviation of the **true** altitude from the commanded altitude |
| `true_alt_min_m`, `true_alt_max_m` | envelope of the true altitude |
| `est_minus_true_rms_m`, `est_minus_true_max_m` | RMS / max of (estimated - true) altitude |
| `dist_bottom_resets`, `z_resets` | number of `dist_bottom` / `z` resets |
| `rng_rejected_fraction` | fraction of range-height samples rejected by the innovation gate |
| `cs_*_fraction` | fraction of time the corresponding EKF fusion flag was set (flow, range height, GPS, ...) |
| `param_*` | the relevant EKF2 / MPC parameters recorded in the log |

## Notes and quirks

* Textures: gz-sim 8 renders a PBR `albedo_map` black unless the material
  also has an explicit `<diffuse>1 1 1 1</diffuse>`; every textured visual in
  the world has it. The flow camera then sees the floor/furniture texture.
* Lighting: ambient 0.7 and the directional light straight down (so the
  walls do not shadow the floor), shadows on. Of the variants tried (angled
  light, shadows off) this gave the most accurate optical flow over the
  furniture; the simulated KLT flow is sensitive to lighting.
* Without GPS the position estimate drifts by roughly 0.3-1 m per obstacle
  crossed (the flow is scaled with `dist_bottom`, which does not match the
  true distance to the obstacle surface, and the simulated tracker is
  disturbed at height discontinuities). The route therefore keeps at least
  1.3 m from every wall, the step is crossed at 1 m/s, and the run is aborted
  (landing immediately) if the estimate is more than 2.5 m from ground truth
  (read through the PX4 shell, ~1 Hz) or 4 m from the setpoint. The vehicle
  never uses ground truth for control. Runs are not deterministic: a run
  can still end early if the drift happens to be large.
* The yaw estimate wanders by up to 10-20 deg relative to the true heading
  during a flight (simulated magnetometer noise, weak yaw observability
  without GPS); every degree rotates the flow velocity and adds drift.
  `EKF2_MAG_TYPE=1` (heading fusion) was tried and was not better.
* Beyond the EKF2 parameters, the script sets `MPC_XY_VEL_MAX=speed+0.3`,
  `MPC_XY_CRUISE=speed`, `MPC_TILTMAX_AIR=20`, `MPC_ACC_HOR(_MAX)=2` (gentle
  manoeuvres keep the simulated flow accurate) and `MPC_LAND_SPEED=0.7`
  (shorter landing). With `--gps` it also sets `SYS_HAS_GPS=1`,
  `SIM_GPS_USED=10` (simulated satellite count; the gz bridge only reports
  a 3D fix from 4) and `EKF2_GPS_CTRL=7`, which airframe 4021 disables;
  without `--gps` these are set to 0 explicitly. The stored parameter files
  in `rootfs/fs` are deleted before every start so that a run never inherits
  parameters from a previous one (a `PX4_PARAM_*` override is stored, and the
  airframe file only uses `param set-default`).
* MAVSDK is only connected after PX4 has printed "Startup script returned
  successfully"; the vehicle heading is taken from `attitude_euler` because
  the `heading` stream never delivered a sample on this setup.
* PX4 SITL writes its logs to `build/px4_sitl_default/rootfs/fs/log/`.
